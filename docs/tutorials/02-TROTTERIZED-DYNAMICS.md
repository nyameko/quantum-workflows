# 2. Trotterized quantum dynamics

## Scientific question

How accurately can a finite quantum circuit approximate the real-time dynamics generated by a
many-body Hamiltonian, and how do product-formula error and finite-shot error differ?

The initial model is the open-boundary transverse-field Ising chain:

$$H=-J\sum_{i=0}^{N-2}Z_iZ_{i+1}-h\sum_{i=0}^{N-1}X_i.$$

The workflow starts from a Néel product state and measures average longitudinal magnetization

$$M_z=\frac{1}{N}\sum_i Z_i.$$

This is intentionally more than a circuit-construction demo. At each time point it computes:

- exact evolution from the matrix exponential (small local systems only);
- second-order Suzuki–Trotter evolution;
- finite-shot sampled magnetization;
- exact-to-Trotter and Trotter-to-sampled errors.

## Run the baseline

```bash
.venv/bin/qw trotter \
  --executor aer \
  --qubits 4 \
  --coupling 1.0 \
  --field 0.7 \
  --final-time 2.0 \
  --time-points 9 \
  --trotter-steps 4 \
  --shots 4096
```

Inspect `data/dynamics.csv`. The two error columns answer different questions:

| Metric | Cause | Reduced by |
| --- | --- | --- |
| `trotter_abs_error` | product-formula approximation | more Trotter steps or a better synthesis method |
| `sampling_abs_error` | estimating probabilities from finite samples | more shots |

On a QPU there is a third contribution: device/transpilation noise. Keeping the exact and noiseless
Trotter baselines makes that contribution observable rather than attributing every deviation to
“quantum noise”.

## Convergence experiment

Run a sweep over `--trotter-steps 1`, `2`, `4`, and `8` with all other inputs fixed. Compare
`rms_trotter_magnetization_error` and circuit depth from `manifest.json`.

Expected tradeoff:

```text
more product-formula repetitions
          │
          ├── lower algorithmic approximation error
          └── deeper circuit → more hardware error and execution cost
```

The optimum on real hardware is not necessarily the most accurate noiseless product formula.

## Hardware execution

The same sampled circuits can be sent directly to IBM:

```bash
.venv/bin/qw trotter --executor ibm --qubits 4 --time-points 5 --shots 4096
```

This submits all time-point circuits in one Sampler job. Start with a small number of points and
inspect estimated usage before scaling. The exact statevector comparison still runs classically
after sampling and is therefore restricted to small qubit counts.

Under Slurm/QRMI:

```bash
sbatch --gres=qpu:1 --qpu=ibm_resource_name slurm/trotter.sbatch
```

## Scaling path

Exact dense evolution grows exponentially and is a reference oracle, not the production method.
The roadmap separates:

- small exact CPU validation;
- Aer CPU sampling;
- Aer/CUDA-Q/PennyLane GPU simulation on A100/H200;
- tensor-network or problem-specific emulation;
- QPU sampling;
- MPI/GPU postprocessing where required.

Future SKQD work will reuse time-evolved states as a Krylov basis, connecting this tutorial directly
to SQD and the larger QCSC chemistry programme.
